# 基准（O-1 / O-2 决策依据）

这两个脚本**不在 `npm test` 内**：它们测量而非断言，数字依赖机器。存在目的是让
O-1（客户端零 memo 化 + 400 卡片截断）与 O-2（journal 体积 / `list()` 成本）的
取舍**由实测决定**，而不是读代码猜。

```sh
node scripts/bench-journal.mjs --steps 500 --runs 20 --payload-kb 8
node scripts/bench-client-render.mjs --sessions 500 --keystrokes 6
```

## 实测结果（Windows / Node 24.12 / jsdom）

### O-2 工作流 journal

| 指标 | 200 步 / 4KB | 500 步 / 8KB |
|---|---|---|
| 单次运行落盘 | 943 KB | **4.36 MB** |

写入量的平方增长**来自 `persist()` 每步重写整份 record**——而 `steps` 数组占
record 载荷的 **96.7%**（实测 120 步：531 KB 里 513 KB）。最初实测：200 步 /
8KB 回复的单次运行**写出 697 MB**。

#### 已修（2026-09 本轮，写入侧）

`steps` 挪到 `<runId>.steps.jsonl`（**只追加**），journal 只保留就地改写的字段
（status / result / log / pendingQuestion…）。**journal 格式本身没变**，因此
`get()` / `amend()` / `resume()` 的读取契约不变——`loadRecord()` 读 journal 再把
JSONL 拼回 `steps`，调用方看不出差别。

| | 200 步 / 8KB 的**单次运行** |
|---|---|
| journal 大小 | 1742.9 KB → **37.1 KB**（47× 小） |
| 每步序列化 | 1.88 ms → **0.08 ms** |
| **整轮写入量** | **697 MB → 5.28 MB** |
| 写放大（写入 ÷ 最终文件） | 400× → **3.2×** |

按步数缩放（同一形状）：

| 步数 | journal | steps JSONL | 落盘合计 | 整轮写入量 |
|---|---|---|---|---|
| 50 | 9.6 KB | 419 KB | 429 KB | 664 KB |
| 200 | 37.1 KB | 1677 KB | 1714 KB | 5.40 MB |
| 500 | 92.2 KB | 4193 KB | 4285 KB | 27.3 MB |

**journal 持平（只装可变状态），JSONL 线性增长，总写入量因此从平方降为线性。**

**残余的线性项**：journal 仍每步重写一次（37 KB × 200 = 3.6 MB），因为 `log`
数组是就地截断的语义。没有继续优化——把 log 也改成追加会牵动 `get()` 的读取
路径与 `MAX_LOG_ENTRIES` 截断语义，收益（常数倍）与风险不成比例。

**数据安全**：追加不是原子的，但**尾部半行可容忍**——读到解析失败的行即停止，
最多丢掉被中断的那一行；而该行对应的步骤在它的 `after` 事件落盘前本就未算完成。
相比旧实现"整份重写被中断即丢整个文件"，损坏面反而更小。

#### 已修（2026-09 本轮，读取侧）

`list()` 曾是**宿主线程上的同步整目录整读**（面板轮询与 `/workflow runs` 反复触发），
且要 `JSON.parse` 每个 journal 的全部 prompt/outcome 正文。修复后 `persist()` 顺带写一份
只含 13 个标量字段的 `<runId>.summary.json`，`list()` 优先读它。

实测（120 个 40 步运行、42 MB journals）：

| | `list()` 每次 |
|---|---|
| 读侧车（新） | **10.9 ms** |
| 整读 journal（旧 / 旧版本遗留目录） | 75.3 ms |
| **提速** | **6.9×** |

外推：100 运行 62 → 9 ms，500 运行 311 → 45 ms，2000 运行 **1245 → 180 ms**。

旧版本留下的运行没有侧车且 steps 内联在 journal 里，两者都会走回落路径——
刻意**不在读路径补写/迁移**，因为 `list()` 是读路径（面板与 `/workflow runs`
都调它），读者不该改存储。


### O-1 客户端渲染 —— **真实浏览器实测：无需修改**

jsdom 侧（`bench-client-render.mjs`，仅供参考，绝对值不可用）：

| 场景 | jsdom 耗时 |
|---|---|
| 400 会话挂载 + 首次拉取 | 213–378 ms（8 493 DOM 节点） |
| 会话过滤框每次按键（20/50/100/200/400 会话） | 8.1 / 17.5 / 26.3 / 115.9 / 170.3 ms |

真实 Chromium（`smoke:real-host` 步骤 8，`SMOKE_PERF_SESSIONS` 可调）：

| 会话数 | 按键中位 | **对照组（双 rAF，无 onChange）** | **净面板开销** |
|---|---|---|---|
| 100 | 33.00 ms | 33.40 ms | **−0.40 ms** |
| 400 | 32.90 ms | 33.20 ms | **−0.30 ms** |
| 800 | 33.30 ms | 33.40 ms | **−0.10 ms** |

**结论：重建 400 张会话卡片在真实 Chromium 里的开销低于本探针的测量噪声（< 1 ms）。
O-1 的"memo 化 / 虚拟化"改动没有性能依据，不建议做。**

#### 这个结论是怎么逼出来的（三次自我否定的记录）

1. **jsdom 报 170 ms/按键** → 我先据此建议"O-1 先做"。CPU profile 否决了它：
   自耗时高度分散（GC 5.5%、jsdom CSS 解析 8.5% 分散在 4 个条目、`installInterfaces`、
   `NamedNodeMap`……），**没有单一热点**；同一份 400 卡片在裸 React + jsdom 里只要
   2.7 ms。绝对毫秒数是 jsdom 的 DOM/CSS 开销，不是我们的代码。**第一次撤回。**
2. 于是补真实浏览器打点。第一版量出"median 0.00 ms"——**假的**：React 18 批处理
   setState，`onChange` 立即返回，渲染还没发生。改为双 rAF 等 commit+paint。
3. 第二版量出"稳定 33 ms"，`100→800 会话全都 ~33 ms`。**又是假的**：33 ms 正好是
   60 Hz 下两帧的节拍。加上"不带 onChange 的双 rAF 对照"后净开销变成 **−0.3 ms**，
   与 33 ms 的差别就是帧时钟本身。
4. 期间还有一次"DOM 从 9 374 崩到 572"，看着像面板重挂载——实际是我的查询
   `perf-0` **只匹配 400 行里的 1 行**。探针现在固定用"匹配全部"的查询，并把
   每次按键后的节点数打印出来当哨兵。

这三层错误都是"量到了漂亮数字但量错了对象"，与 O-2 基准踩的是同一个坑。
因此步骤 8 现在**自带对照组**，并在语料未真正渲染时**拒绝报告数字**。

#### 保留的结构性结论（与环境无关）

- `SESSION_RENDER_CAP = 400` 是**截断而非虚拟化**：800 会话时 DOM 不再增长，
  尾部只能靠过滤触达。这是产品取舍，不是性能问题。
- `sectionState` 的 `patch` 每次渲染都是新函数并作为 prop 传给每张卡片——若将来
  真要加 `React.memo`，**必须先用 `useCallback` 固定它**，否则浅比较永远失败、
  memo 等于没加。这是"加了 memo 却没效果"的典型成因，先记在这里。

### 这份基准的用途边界

| 可信 | 不可信 |
|---|---|
| 相对比较（同环境改前/改后） | 绝对毫秒数 |
| 缩放形状（随卡片数增长） | "是否用户可感" |
| DOM 节点数（与环境无关） | jsdom 与真实浏览器的顺序关系 |

## 结论与建议

- **O-2 已完成两侧**：读取侧（摘要侧车，6.9× / 2000 运行时少阻塞 1.06 s）与
  写入侧（`steps` 走 append-only JSONL，单次运行写入量 697 MB → 5.28 MB，
  写放大 400× → 3.2×，见上）。剩余的线性项（journal 每步重写一次 log 快照）
  刻意保留，见上文说明。
- **O-1 不建议做。** 真实浏览器实测净开销 < 1 ms（见上表），没有性能依据；
  剩下的只有"400 上限是截断"这一条产品取舍问题。
